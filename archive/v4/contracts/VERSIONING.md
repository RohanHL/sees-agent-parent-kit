# Complete versioned handoff and upgrades

The generated bundle contains all seven maintained behavioral modules, its behavior_version, visible module inventory and versioned end marker. These are sufficient for a complete single-file handoff. Missing sections or end marker mean incomplete loading. The adjacent manifest is an optional maintainer integrity companion, not a runtime dependency or another file the parent must provide. The build check verifies exact bytes, not host behavior. When both the manifest and hashing capability are available, compare hashes; otherwise check the visible version, inventory and end marker without claiming cryptographic verification.

Use exactly one complete behavior version per session/run, including scheduled executions. Do not reload individual modules from raw main or replace instructions when refreshing school facts. Maintainers retain the manifest with each release; parents need only the complete generated instruction file and should not assemble dependency order. If links fail, upload or paste the entire generated bundle. It contains all behavioral dependencies; public school facts and private household evidence remain optional independent inputs, not missing behavior.

For a later version: finish or safely pause the current run; validate the new complete bundle and review its changes before switching at a run boundary. Follow host/user approval requirements for changing recurring task instructions. Persist the old version identifier and retain a recoverable private checkpoint when supported. If validation or compatibility fails, continue the known complete old version or stop the affected capability with a clear limit, never a mixed version.

On switching, preserve child-specific completions, corrections, declined offers, source history, delivered-content history, pending proposals and uncertain execution evidence. Reconcile schema changes without resetting known facts. Revalidate proposals against current sources before any execution; a version change never revives expired approvals or makes an uncertain write safe to replay. Preserve only the exact still-valid permissions already granted. New capabilities, new scopes, recipients, cadence or consequential actions require their own authorization. Evidence freshness and behavior revision evolve independently.

A change that materially affects what the parent relies on (access, actions, delivery, continuity) must be explained before it is relied on; avoid meaningless implementation announcements. There is no automatic upgrade service in this kit.
